# Faster voice responses for Sol

Development measurements recorded November 14, 2026. The proposed streaming integrations below are experiments. The primary measure is the time from the user's last spoken word to the first audible word of Sol's actual answer. Measure a listening chime separately. The Mac available for evaluation has an Apple M4 and 16 GB of RAM. The iPhone deployments use a web app or its native wrapper, so a Mac can serve phones over the existing HTTPS LAN preview, while direct on-device integration has different requirements. [Mobile roadmap](mobile-roadmap.md)

## Where Sol waits today

- Voice mode records the full utterance and waits for 640 ms of quiet on short turns or 900 ms on turns longer than 2.2 seconds before calling speech recognition. Speculative snapshots can preload navigation, and the final transcript still drives the response. Both speculative and final server requests use the same single STT executor, so a snapshot can be ahead of final transcription in the queue. [Voice mode](../src/features/assistant/VoiceMode.tsx) · [Turn segmentation](../src/features/assistant/voiceAudio.ts) · [STT client](../src/features/assistant/speechToText.ts) · [Voice server](../voice-server/server.py)
- The server uses faster-whisper `small.en` by default. The browser uses bundled Moonshine Tiny through its batch ONNX pipeline, with Whisper as fallback. Sol computes replies locally through `converse()` using deterministic rules, context and local data. [Voice server](../voice-server/server.py) · [Browser STT worker](../src/features/assistant/whisper.worker.ts) · [Dialogue](../src/features/assistant/dialogue.ts)
- Piper lessac is the default synthesis model in the current browser and server implementations. Kokoro is a browser fallback and can be selected on the server. The playback queue can prepare the next clause while the current one plays. The server and browser worker each return a complete waveform for the current clause and the HTTP client calls `arrayBuffer()` before playback. Emergency openings already have a prerecorded path and device-voice fallback. [TTS server](../voice-server/server.py) · [Browser TTS worker](../src/features/assistant/solVoice.worker.ts) · [Voice client](../src/features/assistant/voiceServer.ts) · [Playback](../src/features/assistant/voiceOutput.ts)

## Local baseline from the existing server

The current server's transcription method was timed on the M4 using two macOS Samantha synthetic English recordings. Eight warm calls per model and clip used the detected MPS backend. These are isolated server method times. They exclude silence gating, HTTP, UI and playback.

| Model | 2.4-second clip median | 6.3-second clip median |
| --- | ---: | ---: |
| `small.en` | 390 ms | 514 ms |
| `base.en` | 134 ms | 202 ms |

`base.en` produced “Cardio Vascular” where `small.en` produced “cardiovascular” on the long clip. Two synthetic files establish a speed baseline. Command and emergency recognition need representative human speech.

A separate eight-call CPU-only pass gave median times of 899 and 4,604 ms for `small.en`, and 1,279 and 425 ms for `base.en`, in short-to-long order. CPU timing varied widely, particularly for the long `small.en` clip (1,156–6,997 ms). For the measured fast path, verify the server logs show MPS.

In a separate Kokoro synthesis benchmark, eight warm calls per reply took a median of 210 ms for “Opening radiation trends.” (197–229 ms range, 1.5 seconds of generated audio) and 412 ms for a longer heart-rate reply (403–458 ms range, 3.6 seconds of audio). This measures complete waveform generation, before playback.

For a short turn with the measured Kokoro timings, adding the 640 ms silence gate to the median STT and short TTS times gives about 1.24 seconds with `small.en` and 0.98 seconds with `base.en`. These sums are estimates before transport, UI, playback and any executor queueing.

## Recommended sequence

1. Compare `base.en` and `small.en` on the current M4 server. Record browser and iPhone times as well as exact command outcomes. Keep speculative snapshots from queuing ahead of final transcription in the batch path.
2. Try Moonshine Tiny and Small Streaming with a persistent audio stream. Use final transcripts to commit dialogue actions. Compare its existing turn detection with Smart Turn only if pauses or early cutoffs remain a problem.
3. Compare the current Kokoro voice through a shorter first-clause or streaming path against Pocket TTS and the system voice. For streamed server audio, consume the body incrementally and start playback once a small buffer of usable audio arrives. Keep playback interruptible across chunks and measure the delay to the first voiced sample.
4. Take end-to-first-answer medians and p95s with warm and cold sessions. Break the timing down into endpoint, final transcript, reply text, and first audible word. Include short commands, longer pauses, speech over background noise, compound words, emergency terms and realistic microphone input. Compare false cutoff rates, exact action accuracy and interruptions across the desktop and iPhone.
